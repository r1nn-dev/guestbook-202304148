# 강제 삭제는 별도 관리자 화면 없이 기존 삭제 요청에서 관리자 비밀번호를 먼저 비교한다

관리자는 따로 로그인하거나 관리자 전용 엔드포인트를 쓰지 않는다. 글쓴이와 같은 삭제 폼과 같은 `DELETE /api/entries/[id]` 요청으로 강제 삭제한다. 서버는 입력 검증(400)을 통과한 비밀번호를 글 해시보다 먼저 환경 변수 `ADMIN_PASSWORD`와 비교한다. 맞으면 바로 삭제하고, 틀리면 기존 흐름(404 → 403 → 204)으로 이어간다. 관리자 화면·세션·쿠키를 새로 만드는 비용 없이 "어떤 글이든 지울 수 있다"는 요구만 채우기 위해 이렇게 정했다. 이전에 정했던 "관리자 삭제 기능은 두지 않는다"는 결정은 이것으로 대체한다.

## Considered Options

- **관리자 로그인 + 관리자 화면:** 세션 관리, 화면, 인증 흐름이 새로 필요해 과제 범위와 시간에 비해 너무 크다.
- **별도 관리자 삭제 엔드포인트:** 화면에 관리자용 입력이 또 필요하고, 삭제 로직이 둘로 나뉜다.

## Consequences

- 비교는 양쪽을 SHA-256으로 같은 길이로 만든 뒤 `timingSafeEqual`로 한다. 길이 차이로 예외가 나거나 정보가 새지 않게 하기 위해서다.
- `ADMIN_PASSWORD`가 없거나 비어 있으면 강제 삭제는 꺼진다. 어떤 입력도 관리자 비밀번호로 통과하지 않는다.
- 관리자 비밀번호도 삭제 입력 검증(4~50자)을 먼저 거친다. 그래서 `ADMIN_PASSWORD`는 50자 이하여야 한다. rate limit이 없으므로 무차별 대입에 버티도록 16자 이상의 무작위 값을 쓴다. 규칙은 16~50자다.
- 로컬 `.env.local`과 Vercel 양쪽에 같은 값을 설정해야 한다. 두 환경이 같은 DB를 쓰기 때문이다(ADR 0002).
- 강제 삭제의 응답은 일반 삭제와 같은 204다. 응답만으로 관리자가 지웠는지 알 수 없다.
- 관리자는 삭제만 할 수 있고 수정은 할 수 없다. 수정은 계속 글 비밀번호로만 한다.
- 어떤 글의 글 비밀번호가 우연히 관리자 비밀번호와 같아도 결과는 삭제로 같으므로 문제가 없다.
