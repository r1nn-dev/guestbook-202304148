# 미니 방명록

## Problem Statement

방문자가 회원가입이나 로그인 없이 짧은 글을 남기고, 남겨진 글 전체를 한눈에 볼 수 있는 곳이 없다. 방문자는 자기가 남긴 글을 나중에 고치거나 지울 수 있어야 한다. 하지만 계정이 없으니 다른 사람이 그 글을 건드리지 못하게 막을 방법도 필요하다. 이 앱은 시험 과제이기도 하므로, 누가 만들었는지(개발자 정보)가 화면에 항상 보여야 한다.

## Solution

한 페이지짜리 방명록을 만든다. 방문자는 작성자 이름, 메시지, 글 비밀번호를 입력해 글을 남긴다. 방명록에는 모든 글이 최신 작성 순으로 보인다. 각 글 안에서 "수정" 또는 "삭제"를 누르면 글 비밀번호 입력칸이 펼쳐진다. 비밀번호가 맞으면 글쓴이로 인정되어 메시지를 고치거나 글을 지울 수 있다. 틀리면 그 글 안에 "비밀번호가 일치하지 않습니다."가 표시된다. 수정된 글에는 "(수정됨)"이 붙는다. 화면 상단과 푸터에는 개발자 정보(이름과 학번)가 표시된다.

용어는 `CONTEXT.md`의 용어집을 따른다. 특히 **글쓴이**는 회원이 아니라 "그 글의 글 비밀번호를 아는 사람"이다.

## User Stories

### 글 남기기

1. 방문자로서, 회원가입 없이 작성자 이름, 메시지, 글 비밀번호만 입력해 글을 남기고 싶다. 그래야 부담 없이 방명록에 참여할 수 있다.
2. 방문자로서, 이름을 1~20자로 입력할 수 있기를 원한다. 그래야 짧은 표시용 이름을 쓸 수 있다.
3. 방문자로서, 메시지를 1~500자로 입력할 수 있기를 원한다. 그래야 충분히 말하되 방명록이 지나치게 길어지지 않는다.
4. 방문자로서, 글 비밀번호를 4~50자로 정할 수 있기를 원한다. 그래야 나중에 내 글을 고치거나 지울 수 있다.
5. 방문자로서, 이름과 메시지 앞뒤에 실수로 넣은 공백이 저장되지 않기를 원한다. 그래야 글이 깔끔하게 보인다.
6. 방문자로서, 공백만 입력한 이름이나 메시지는 거부되기를 원한다. 그래야 비어 보이는 글이 생기지 않는다.
7. 방문자로서, 글 비밀번호는 입력한 그대로(공백 포함) 저장되기를 원한다. 그래야 내가 정한 값이 곧 비밀번호가 된다.
8. 방문자로서, 입력이 규칙에 맞지 않으면 무엇이 잘못됐는지 한 문장으로 안내받고 싶다. 그래야 바로 고쳐서 다시 제출할 수 있다.
9. 방문자로서, 여러 칸이 한꺼번에 틀렸을 때는 이름 → 메시지 → 비밀번호 순서로 첫 번째 문제만 안내받고 싶다. 그래야 안내가 간단하다.
10. 방문자로서, 이모지가 섞인 메시지도 눈에 보이는 글자 수대로 세어지기를 원한다. 그래야 500자 제한이 예상대로 동작한다.
11. 방문자로서, 글을 남기면 입력칸이 비워지고 내 글이 방명록 맨 위에 바로 보이기를 원한다. 그래야 등록이 됐는지 확신할 수 있다.
12. 방문자로서, 등록 중에는 버튼을 다시 누를 수 없기를 원한다. 그래야 같은 글이 두 번 올라가지 않는다.
13. 방문자로서, 메시지의 줄바꿈이 그대로 보이기를 원한다. 그래야 여러 줄로 쓴 글이 의도대로 읽힌다.
14. 방문자로서, 메시지에 HTML이나 스크립트를 넣어도 글자로만 보이기를 원한다. 그래야 다른 방문자가 안전하다.
15. 방문자로서, 다른 사람과 같은 작성자 이름을 써도 글을 남길 수 있기를 원한다. 작성자 이름은 누구인지 증명하는 값이 아니기 때문이다.

### 방명록 보기

16. 방문자로서, 로그인 없이 전체 글을 보고 싶다. 그래야 누구나 방명록을 읽을 수 있다.
17. 방문자로서, 글이 최신 작성 순으로 정렬되기를 원한다. 그래야 새 글을 먼저 볼 수 있다.
18. 방문자로서, 작성 시각이 같은 글끼리는 나중에 등록된 글이 위에 오기를 원한다. 그래야 순서가 항상 일정하다.
19. 방문자로서, 각 글의 작성자 이름, 메시지, 작성 시각을 보고 싶다.
20. 방문자로서, 작성 시각이 한국 시간(KST)으로 `YYYY. MM. DD. HH:mm` 형식으로 보이기를 원한다. 그래야 서버가 어디에 있든 익숙한 시각으로 읽을 수 있다.
21. 방문자로서, 수정된 글에는 "(수정됨)"이 붙기를 원한다. 그래야 처음 쓴 글과 달라졌다는 것을 알 수 있다.
22. 방문자로서, 글이 수정돼도 방명록에서의 순서는 바뀌지 않기를 원한다. 정렬 기준은 작성 시각이기 때문이다.
23. 방문자로서, 페이지를 새로 열 때마다 최신 방명록을 보고 싶다. 그래야 방금 올라온 다른 사람의 글도 보인다.
24. 방문자로서, 글이 하나도 없을 때는 첫 글을 남겨보라는 안내를 보고 싶다.
25. 방문자로서, 전체 글이 몇 개인지 보고 싶다.

### 수정하기

26. 글쓴이로서, 내 글 안에서 "수정"을 누르면 현재 메시지가 채워진 편집칸과 글 비밀번호 입력칸이 펼쳐지기를 원한다. 그래야 다른 화면으로 가지 않고 고칠 수 있다.
27. 글쓴이로서, 글 비밀번호가 맞으면 메시지를 고칠 수 있기를 원한다.
28. 글쓴이로서, 작성자 이름은 고칠 수 없고 메시지만 고칠 수 있다는 것을 분명히 알고 싶다.
29. 글쓴이로서, 고친 메시지에도 작성할 때와 같은 규칙(trim, 1~500자)이 적용되기를 원한다.
30. 글쓴이로서, 메시지를 그대로 두고 저장해도 거부되지 않기를 원한다. 이 경우에도 "(수정됨)"이 붙는다.
31. 글쓴이로서, 수정에 성공하면 편집칸이 닫히고 고친 메시지와 "(수정됨)"이 바로 보이기를 원한다.
32. 방문자로서, 남의 글을 틀린 비밀번호로 수정하려 하면 거부되고 그 글 안에 "비밀번호가 일치하지 않습니다."가 표시되기를 원한다. 그래야 글쓴이만 글을 고칠 수 있다.
33. 글쓴이로서, 비밀번호를 틀려도 편집칸이 닫히지 않고 입력한 메시지가 남아 있기를 원한다. 그래야 비밀번호만 다시 입력하면 된다.
34. 글쓴이로서, 메시지가 규칙에 맞지 않으면 비밀번호 확인보다 먼저 입력 오류를 안내받고 싶다.
35. 글쓴이로서, "취소"를 누르면 편집칸이 닫히고 원래 메시지가 보이기를 원한다.
36. 글쓴이로서, 고치는 사이에 글이 이미 지워졌다면 "글을 찾을 수 없습니다."를 그 글 안에서 안내받고 싶다.

### 삭제하기

37. 글쓴이로서, 내 글 안에서 "삭제"를 누르면 글 비밀번호 입력칸이 펼쳐지기를 원한다.
38. 글쓴이로서, 글 비밀번호가 맞으면 글이 삭제되고 방명록에서 바로 사라지기를 원한다.
39. 글쓴이로서, 비밀번호 입력 자체를 확인 절차로 보고 별도의 확인 창 없이 삭제되기를 원한다.
40. 방문자로서, 남의 글을 틀린 비밀번호로 지우려 하면 거부되고 그 글 안에 "비밀번호가 일치하지 않습니다."가 표시되기를 원한다.
41. 글쓴이로서, 이미 지워진 글을 지우려 하면 "글을 찾을 수 없습니다."를 안내받고 싶다.
42. 글쓴이로서, "취소"를 누르면 입력칸이 닫히기를 원한다.
43. 방문자로서, 여러 글의 수정·삭제 입력칸을 동시에 열어도 각 글의 안내가 서로 섞이지 않기를 원한다.

### 개발자 정보

44. 채점자로서, 화면 상단에서 개발자 이름과 학번을 보고 싶다.
45. 채점자로서, 푸터에서도 개발자 이름과 학번을 보고 싶다.

### 보안과 데이터

46. 글쓴이로서, 내 글 비밀번호가 원문으로 저장되지 않기를 원한다. 그래야 DB가 유출돼도 비밀번호가 드러나지 않는다.
47. 글쓴이로서, 같은 비밀번호를 쓰는 다른 글과도 저장된 해시가 달라지기를 원한다(글마다 무작위 salt).
48. 방문자로서, 어떤 응답에도 글 비밀번호나 그 해시가 포함되지 않기를 원한다.
49. 글쓴이로서, 비밀번호 비교에 걸리는 시간으로 정답을 추측할 수 없기를 원한다.
50. API 사용자로서, 잘못된 요청은 400, 없는 글은 404, 비밀번호 불일치는 403으로 구분해 받고 싶다. 그래야 화면이 알맞은 안내를 보여줄 수 있다.
51. API 사용자로서, 모든 오류 응답이 같은 모양(안내 문구 하나)이기를 원한다. 그래야 화면이 받은 문구를 그대로 보여주면 된다.
52. API 사용자로서, 글 번호가 양의 정수가 아니면 400을 받고 싶다.
53. API 사용자로서, JSON이 아닌 본문을 보내도 서버가 죽지 않고 400을 받기를 원한다.

## Implementation Decisions

### 스택과 구조

- Next.js App Router(16.x)와 TypeScript, Neon Postgres(`@neondatabase/serverless`)를 쓰고 Vercel에 배포한다. ORM 없이 `sql` 태그드 템플릿으로 쿼리한다.
- 이 버전의 Next.js는 학습 데이터와 다를 수 있다. 구현 전에 `node_modules/next/dist/docs/`의 관련 문서를 읽는다. 확인된 사항은 다음과 같다.
  - 동적 라우트 핸들러의 `params`는 Promise다.
  - `cacheComponents`가 꺼져 있으므로 `export const dynamic = "force-dynamic"`을 쓸 수 있다.
- 화면은 `/` 한 페이지다. 방명록을 읽는 페이지는 `force-dynamic`으로 요청마다 렌더링한다.
- 서버 로직은 API Routes에 둔다. Server Actions는 쓰지 않는다.
- 로컬과 배포는 같은 Neon DB 하나를 쓰고, 마이그레이션 러너는 두지 않는다(ADR 0002).

### 모듈

- **입력 검증 모듈(순수):** 작성·수정·삭제 요청 본문과 글 번호를 받아 `{ ok: true, value }` 또는 `{ ok: false, error }`를 돌려준다.
  - 작성 입력: 이름·메시지는 trim한 뒤 검사한다. 비밀번호는 원본 그대로 검사한다.
  - 수정 입력: 메시지와 비밀번호만 본다. 이름이 들어와도 무시한다.
  - 삭제 입력: 비밀번호만 본다.
  - 글 번호: 앞자리가 0이 아닌 1~18자리 양의 정수 문자열만 허용한다. bigint 범위를 넘는 값이 DB 오류로 번지지 않게 하기 위해서다.
  - 글자 수는 코드포인트 기준으로 센다. Postgres `char_length`와 같게 맞춰서, API 검증은 통과하고 DB CHECK에서 걸리는 불일치를 없앤다.
  - 여러 필드가 틀리면 이름 → 메시지 → 비밀번호 순서로 첫 오류 하나만 돌려준다.
  - 문자열이 아닌 값과 객체가 아닌 본문(null, 배열, 문자열)은 거부한다.
  - 안내 문구와 길이 제한 상수도 이 모듈이 소유한다. 화면 입력칸의 제한값도 같은 상수를 쓴다.
- **글 비밀번호 모듈(순수):** `hash(비밀번호) → 저장 문자열`과 `verify(비밀번호, 저장 문자열) → boolean`.
  - `node:crypto` scrypt를 쓴다. salt는 16바이트, 키는 64바이트이고, hex 문자열 `salt:hash`로 저장한다(ADR 0001).
  - 비교는 `timingSafeEqual`로 한다.
  - 저장 문자열의 형식이 깨졌으면(콜론 없음, 빈 조각, 키 길이 불일치) 예외를 던지지 않고 false를 돌려준다.
- **KST 표시 함수(순수):** ISO 시각 문자열을 받아 `Asia/Seoul` 기준 `YYYY. MM. DD. HH:mm`(24시간제)로 돌려준다.
- **글 저장소 모듈:** Neon 쿼리를 감싼다. 목록, 작성, 비밀번호 해시 조회, 메시지 수정, 삭제를 제공한다.
  - `select *`를 쓰지 않고 컬럼을 하나하나 지정한다. 응답용 글 모양에는 `password_hash`가 없다.
  - 수정·삭제는 대상 행이 없으면 "없음"을 돌려준다. 비밀번호 확인과 실제 변경 사이에 글이 지워진 경우를 처리하기 위해서다.
  - DB 행의 컬럼 이름(snake_case)을 응답의 camelCase로 바꾸는 일도 이 모듈이 맡는다.
- **DB 클라이언트:** `DATABASE_URL` 환경 변수로 Neon 클라이언트를 만든다. 값이 없으면 분명한 오류를 낸다.
- **개발자 정보 상수:** 이름 "조하린", 학번 "202304148". 사용자가 `lib/developer.ts`에 두라고 지정했다.
- **화면:**
  - 방명록 페이지(서버 컴포넌트)가 목록을 읽고, 작성 시각을 KST 문자열로 바꿔 넘긴다.
  - 작성 폼과 글 항목은 클라이언트 컴포넌트다.
  - 글 항목의 상태는 보기 / 수정 / 삭제 세 가지이고, 오류 안내는 그 글 안에 둔다.
  - 요청이 성공하면 `router.refresh()`로 서버 렌더링된 목록을 다시 받는다. 클라이언트에서 목록 상태를 따로 들고 있지 않는다.
  - 요청을 처리하는 동안에는 제출 버튼을 비활성화한다.
  - 레이아웃 상단과 푸터에 개발자 정보를 표시한다.
  - UI는 한국어이고 Tailwind로 간단하게 꾸민다. 템플릿의 기본 전역 스타일(배경색, 다크 모드 변수)은 Tailwind 클래스와 충돌하므로 정리한다.

### 스키마

- 스키마는 이미 Neon에서 실행했다. `db/schema.sql`은 기록용 사본이며 자동으로 실행되지 않는다.
- `entries` 테이블의 컬럼은 다음과 같다.
  - `id bigserial pk`
  - `name text not null`, 1~20자 check
  - `message text not null`, 1~500자 check
  - `password_hash text not null`
  - `created_at timestamptz default now()`
  - `updated_at timestamptz null`
- `created_at desc` 인덱스가 있다. 스키마는 바꾸지 않는다.

### API 계약

모든 본문은 JSON이다. 응답의 글 모양은 `{ id: string, name: string, message: string, createdAt: ISO string, updatedAt: ISO string | null }`이다. 오류 응답은 항상 `{ error: string }`이다.

| 요청 | 성공 | 실패 |
| --- | --- | --- |
| `GET /api/entries` | 200, 글 배열(최신 작성 순, 같으면 id 큰 순) | — |
| `POST /api/entries` `{ name, message, password }` | 201, 생성된 글 | 400 |
| `PATCH /api/entries/[id]` `{ message, password }` | 200, 수정된 글(`updated_at = now()`) | 400 / 404 / 403 |
| `DELETE /api/entries/[id]` `{ password }` | 204, 본문 없음 | 400 / 404 / 403 |

- 수정·삭제의 판정 순서는 400(글 번호 → 본문) → 404(글 없음) → 403(비밀번호 불일치)이다. DB 없이 할 수 있는 검사를 먼저 한다.
- JSON 파싱에 실패하면 본문이 없는 것으로 보고 400을 돌려준다.

안내 문구는 다음과 같다.

| 상황 | 문구 |
| --- | --- |
| 본문 오류 | 잘못된 요청입니다. |
| 글 번호 오류 | 잘못된 글 번호입니다. |
| 이름 | 이름은 1~20자로 입력해주세요. |
| 메시지 | 메시지는 1~500자로 입력해주세요. |
| 비밀번호 형식 | 비밀번호는 4~50자로 입력해주세요. |
| 403 | 비밀번호가 일치하지 않습니다. |
| 404 | 글을 찾을 수 없습니다. |
| 네트워크 실패(클라이언트) | 서버에 연결하지 못했습니다. |

## Testing Decisions

- **도구:** Vitest. 자동 테스트는 DB에 닿지 않는 순수 로직만 다룬다. DB 통합 테스트와 E2E는 하지 않는다.
- **좋은 테스트의 기준:** 모듈의 공개 함수에 입력을 넣고 결과만 확인한다. 내부 헬퍼나 구현 방식(정규식, 파라미터 값 자체)은 검증하지 않는다. 경계값과 거부 사례를 표 형태(`it.each`)로 촘촘히 다룬다.
- **Seam (사용자 확인 완료):**
  1. **입력 검증 모듈**
     - 이름·메시지 trim과 비밀번호 무변형
     - 공백뿐인 값, 20/21자, 500/501자, 3/4/50/51자 경계
     - 이모지를 한 글자로 세는지
     - 문자열이 아닌 값, 객체가 아닌 본문
     - 여러 오류 중 첫 번째 하나만 돌려주는 순서(이름 → 메시지 → 비밀번호)
     - 수정 입력에서 이름을 무시하는지, 메시지 오류가 비밀번호 오류보다 먼저인지
     - 글 번호 허용(1, 42, 18자리)과 거부(0, -1, 01, 1.5, abc, 빈 문자열, 19자리)
  2. **글 비밀번호 모듈**
     - `salt:hash` hex 형식
     - 같은 비밀번호라도 매번 다른 결과
     - 원문 비밀번호를 포함하지 않음
     - 맞는 비밀번호는 통과, 틀린 비밀번호와 공백 차이는 거부
     - 형식이 깨진 저장값은 false
  3. **KST 표시 함수**
     - UTC → KST 변환
     - KST 기준으로 연·월·일이 넘어가는 경계
- **자동 테스트하지 않는 것:** API 라우트의 판정 순서와 상태 코드, 저장소 쿼리, 화면 동작. 이 부분은 개발 서버에서 수동으로 확인한다.
  - 로컬과 배포가 같은 DB를 쓰므로, 수동 확인으로 만든 글은 끝나면 지운다.
  - Windows curl은 한글 인자를 CP949로 보내 글자가 깨진다. 한글 입력은 UTF-8 본문으로 보낸다(예: Node `fetch`).
- **기존 테스트:** 저장소에 아직 테스트가 없다. Vitest를 새로 들이고 `test` 스크립트를 추가한다.
  - Vitest 5는 `@types/node` 22 이상을 요구하므로 현재의 20에서 올려야 한다.
